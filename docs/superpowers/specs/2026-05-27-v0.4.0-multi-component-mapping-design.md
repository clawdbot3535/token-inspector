# v0.4.0 — Multi-component mapping (mapping-first) — Design

**Date:** 2026-05-27
**Status:** Approved (pending spec review)
**Branch:** `feat/v0.4.0-multi-component-mapping` (off `main` @ `13ecd67`)
**Supersedes/extends:** the PR 4b plan (`docs/superpowers/plans/2026-05-21-tailwind-utility-first-pr4b-scan-view-and-release.md`) — its Scan View work is folded in here, plus the multi-component mapping work.

---

## Problem

The recipe **output** (Nuxt UI `app.config.ts` recipes) is the inspector's core adapter value, but it is gated to a single component: `app-config.ts:45 → COMPONENT_ALLOW_LIST = ["button"]`. The real Figma file has ~18 component groups (badge, input, card, dropdown, modal, checkbox, radio, switch, chip, textarea, nav, table, progress, kbd, …) whose tokens currently produce "No Tailwind utility mapping" and no recipes. The user's priority for v0.4.0: **the Nuxt/Tailwind mapping must work really well across the standard component set** — previews are secondary.

The Figma tokens themselves are work-in-progress and contain errors/inconsistencies. The mapping must be **robust** to that: never crash, degrade gracefully, and surface gaps as actionable readiness data rather than breaking output.

## Goal

Ship v0.4.0 with: (1) the recipe output + scan expanded from `button`-only to the **full standard component set**; (2) the slot-mapping **vocabulary hardened (Approach A)** so the core set maps to high coverage; (3) the **Scan View** (PR 4b) as the instrument that surfaces mapping quality and source inconsistencies; (4) Figma-PAT references purged; (5) a tagged v0.4.0 release.

Long-term the mapping goes to **Approach B** (per-component sub-element slots). v0.4.0 is Approach A, **architected so B extends cleanly** (additive, not a rewrite).

## Non-goals (v0.4.0)

- **Sub-element slots (Approach B, mapping category 3):** `item-*`, `thumb-*`, `dot-*`, `check-*`, `th-*`, `td-*`, `row-*`, `track-*`, `fill-*` → Nuxt UI recipe slots. Deferred to v0.5.0+ (one component per release). v0.4.0 only stubs the extension point.
- **Component previews** (`LiveBadge`, `LiveInput`, …) — secondary; deferred to v0.5.0+. Only `button` keeps its live preview.
- **Non-standard / structural sets:** `button-overlay-dark`/`-light`, `nav-overlay` — left out of the allow-list; the Scan View flags them.
- **Tolerating inconsistent token orderings** in the heuristic (e.g. `chip-bg-error` suffix vs `badge-default-bg` prefix). Those "Knackpunkte" are surfaced by the Scan View and fixed at the source (Figma), not papered over with heuristic acrobatics.

## Mapping gap analysis (the real source data)

Running the real `components/global.tokens.json` tokens through the current grammar shows the gaps are **systematic**, in four categories:

| Category | Examples | Components affected | v0.4.0? |
|---|---|---|---|
| **1. Missing utility types** | `height`, `width`, `line-height`, `letter-spacing`, `placeholder`, `ring-offset`, `font-family`, `padding`, `overlay-bg` | button, input, textarea, card, modal, kbd, badge, nav | ✅ yes |
| **2. Color-role variant axis** | `badge-default-bg`, `badge-accent-text` (role in **prefix** position) | badge, chip, form controls | ✅ yes (prefix only) |
| **3. Sub-element slots** | `nav-item-bg`, `switch-thumb-color`, `table-th-bg`, `progress-track-bg` | checkbox, radio, switch, nav, dropdown, table, progress | ❌ v0.5.0+ |
| **4. Extra state keys** | `checked`, `hovered` | checkbox, radio, switch | ✅ yes |

Approach A = categories 1 + 2 + 4. It lifts the **core set** (button, badge, input, textarea, card, modal, kbd, chip) to high coverage. Category-3 components appear in the Scan View as partially mapped — the honest signal that drives the v0.5.0 work.

## Design

### 1. Allow-list expansion

`COMPONENT_ALLOW_LIST` (in `src/renderers/app-config.ts`) grows from `["button"]` to the standard set:
`button, badge, input, textarea, card, modal, kbd, chip, checkbox, radio, switch, nav, dropdown, table, progress`.
The same list feeds the scanner/recipe `components` option (and `useScanReport`). Category-3 components emit only what maps (partial recipes) and surface as low readiness — partial output is acceptable and the existing `// Incomplete in Figma: missing X` annotations apply.

### 2. Slot-mapping hardening (`src/slot-mapping.ts` + `src/recipe-engine.ts`)

Each new utility type must be wired **end-to-end**: recognized in `slot-mapping.ts` (utility string → `UtilityType`) **and** rendered in `recipe-engine.ts` (`UtilityType` → Tailwind class). New `UtilityType`s and their Tailwind families:

| UtilityType | utility strings | Tailwind family |
|---|---|---|
| `height` | `height`, `min-height` (→`min-height`)*, `size` | `h-*` / `size-*` |
| `width` | `width` | `w-*` |
| `line-height` | `line-height`, `leading` | `leading-*` |
| `letter-spacing` | `letter-spacing`, `tracking` | `tracking-*` |
| `placeholder-color` | `placeholder` | `placeholder:text-*` (color) |
| `ring-offset` | `ring-offset` | `ring-offset-*` |
| `font-family` | `font-family` | `font-*` |
| `padding` | `padding` | `p-*` |
| `overlay-bg` | `overlay-bg`, `overlay` | `bg-*` (color) |

\* keep `min-height` distinct if the engine needs `min-h-*`; otherwise fold into `height`. The plan resolves the exact split.

**Color-role variant axis (category 2):** introduce `COLOR_ROLE_KEYS = { default, accent, primary, secondary, success, error, warning, info, neutral }` (shared with the scanner's `KNOWN_VARIANT_NAMES` — extract one constant, single source of truth). In `parseSegments`, the 2nd segment is a **color role** when it is in `COLOR_ROLE_KEYS` (and not already a button-style `VARIANT_KEYS` member). It produces `variantAxis: "color"`, `variantKey: <role>` (the `"color"` axis already exists in the `VariantAxis` type but is currently unused). Recognized only in the **prefix** position (`<component>-<role>-<utility>`). Suffix orderings stay unmapped → Scan View flag.

**State keys (category 4):** add `checked`, `hovered` to `STATE_KEYS`. Normalize Figma naming to Tailwind pseudo-classes: `hovered → hover`, `checked → checked`. (`active`/`disabled`/`focus`/`hover` already handled.)

**Approach-B extension point:** add a `SLOT_PREFIXES: ReadonlyMap<string, RecipeSlot>` (e.g. `item`, `thumb`, `track`, `fill`, `th`, `td`, `row`, `dot`, `check`, `close-icon`, `label`) recognized in `parseSegments` right after the component segment. In v0.4.0 it is **empty/minimal** (only the existing `label`-style cases if any), so behavior is unchanged — but v0.5.0 fills it per component without restructuring the parser. Document it as the B seam.

### 3. Robustness contract

- `heuristicSlotMapping` returns `null` for any unrecognized/inconsistent token (already true) — no throw.
- `buildGraph` / renderers / scanner never throw on malformed or inconsistent Figma tokens; problems become `GraphIssue` / `ScanIssue` entries.
- Enabling the full allow-list must not break the build or output on messy tokens — unmapped tokens simply don't emit and show up in the Scan View readiness table.
- A test feeds deliberately inconsistent tokens (suffix color-role, unknown utility, sub-element) and asserts: no throw, those tokens are absent from the recipe output, and they appear as gaps/issues in the scan report.

### 4. Scan View (folds in PR 4b)

Per the PR 4b plan: `useScanReport` composable (now scoped to the full allow-list, not `["button"]`), `ScanView.vue` (category accordions + **component-readiness table** + output-forecast line), `HeaderStatusStrip.vue` (compact permanent strip), LiveButton `n/m` completeness badge, and **remove `IssuesView.vue`** (absorbed). `state.ts` `ViewMode` becomes `'inspector' | 'scan'`. The readiness table is the mapping-quality / WIP instrument.

### 5. Figma-PAT cleanup

Purge the dead "Figma PAT integration" rationale from `CHANGELOG.md` (`[Unreleased]`) and the component-aware-preview hint in the app (the "until the Figma PAT integration lands" copy → "until their own live preview lands (v0.5.0+)"). The README is already done.

### 6. Release

Version bump to `0.4.0`, CHANGELOG `[0.4.0]` entry (scanner + Scan View + multi-component mapping + cleanup), README "Token Scan" + multi-component note, tag `v0.4.0`. Push/tag/GitHub-release are the user's action (external writes are blocked for the agent).

## Testing

- **Slot-mapping unit tests:** each new utility type (recognition), color-role prefix axis (`badge-default-bg → bg-color, color/default`), state keys (`...-checked`, `...-hovered → hover`), and the B extension point existing-but-empty (no behavior change).
- **Recipe-engine unit tests:** each new `UtilityType` renders the correct Tailwind class; color-role variant buckets emit correctly.
- **Robustness test:** inconsistent/messy tokens degrade gracefully (no throw, absent from output, present as scan gaps).
- **Scan View / composable tests:** `useScanReport` over the full allow-list; ScanView renders categories + readiness + forecast; HeaderStatusStrip counts.
- **Coverage check (manual/CLI):** run the scan over the real `components/*.tokens.json` and confirm the core set (button/badge/input/textarea/card/modal/kbd/chip) reaches high readiness; record the category-3 components' partial state as the v0.5.0 backlog.
- Existing 194 tests stay green.

## Risks / open items

- **New utility → Tailwind class accuracy:** each new `UtilityType` must render a valid Tailwind v4 class; verified by recipe-engine tests + a CLI spot-check against real tokens.
- **Color-role ↔ button-variant collision:** a token's 2nd segment is matched against `VARIANT_KEYS` first, then `COLOR_ROLE_KEYS`; the sets are disjoint, so no ambiguity. (`primary`/`secondary` are color roles, not button variants — consistent with Nuxt UI.)
- **Partial recipes for category-3 components:** acceptable; flagged by readiness + completeness annotations. If the sparse output is noisy, the allow-list can defer the worst offenders — decided during the plan via the real scan output.
- **Source inconsistencies are WIP:** the Scan View is the tracker; some gaps are resolved in Figma, not in code.
